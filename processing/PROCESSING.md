# AuthBench Processing Pipeline (Current Codebase)

Stages:
1. Build & Normalization
Standardize raw rows from heterogeneous sources into a shared schema, tokenize and chunk long documents, apply basic dirty-text filtering, and keep a bounded reservoir of documents per author to form the initial author-filtered corpus.

2. Quality Filtering
Normalize text artifacts, recompute token statistics, and remove documents with low information content, excessive symbol noise, or language/script inconsistencies.

3. Redundancy Reduction
Remove exact duplicate documents, detect near-duplicate texts using SimHash, and eliminate highly similar author profiles across sources.

4. Language Audit
Verify language labels using script checks and optional language detection, retagging or dropping documents with high-confidence mismatches.

5. Bucket Balanced Sampling
Construct the final benchmark by sampling documents to meet target distributions across languages, genres, and document-length buckets, then write the final train/dev/test splits and retrieval files.

---

This document replaces the old split between `PROCESSING.md` and `FLOW.md`.
It describes how the benchmark is actually constructed in the current codebase,
starting from raw dataset manifests and ending at the exported retrieval files.

The main entrypoints are:

```bash
python -m processing.construct_benchmark
python -m processing.second_phase_web_crawling.run_pipeline
python -m processing.combine_phase_benchmarks
```

## 1. Pipeline at a Glance

The codebase currently builds the benchmark in three layers:

1. Phase 1 construction from the primary manifest in `processing/datasets_manifest.json`.
2. Phase 2 web crawl plus the same construction pipeline over the crawled corpora.
3. Optional merge of the finalized phase 1 and phase 2 outputs into one combined benchmark.

Inside `processing.construct_benchmark`, the pipeline is:

1. Stage 1: build and normalize an author-filtered corpus.
2. Stage 2: quality filtering.
3. Stage 3: redundancy reduction.
4. Stage 4: language audit.
5. Stage 5: bucket balanced sampling, split, and export.
6. Monitoring: write one unified summary/report for the whole run.

## 2. Stage 1: Build & Normalization

### 2.1 Manifest-driven ingestion

The constructor reads a manifest and turns each dataset entry into a `DatasetConfig`
via `processing/datasets.py`.

Supported loaders in the current code are:

- `jsonl`
- `csv`
- `tsv`
- `hf_streaming`
- `blog_authorship`

Each manifest entry maps source-specific fields onto the common raw schema:

- `raw_id`
- `author`
- `text`
- `lang`
- `source`
- `genre`
- `metadata`

### 2.2 Current phase 1 manifest

`processing/datasets_manifest.json` currently includes:

- `blog_authorship`

- `xiaohongshu`
- `douban_reviews`
- `hindi_discourse`
- `spanish_pd_books`
- `french_pd_books`
- `arabic_poetry`
- `russian_pd`
- `german_pd`

### 2.3 Current phase 2 manifest

`processing/second_phase_web_crawling/datasets_manifest.json` is generated by
`processing.second_phase_web_crawling.build_manifest` from the crawled corpora.
It currently covers:

- `stackexchange`
- `project_gutenberg`
- `wikisource`
- `ytcomments`

### 2.4 Source normalization

Normalization happens inside stage 1 before any downstream filtering or sampling:

1. Source-specific preprocessors may rewrite rows.
   Examples: `arxiv_first_author`, `hindi_story_author`.
2. Genre labels are standardized through `processing.config.genre_mapper_for_source`.
3. Missing `raw_id` values are synthesized as `<source>:<row_idx>`.
4. Language codes are lowercased, with `static_lang` used when the dataset has no language field.

The benchmark does not keep raw author names in the final output. Authors are
hashed later as `sha256(f"{source}:{raw_author}")`, so author IDs are source-local
and privacy-preserving.

## 3. Stage 1 Details: Build & Normalization

Implementation: `processing/build_benchmark.py`

This stage is responsible for standardizing raw inputs and keeping as many usable
documents as possible before the stricter cleanup and balancing stages. In the
unified constructor, it runs with `defer_sampling=True`, so it does not enforce
the final benchmark size.

### 3.1 Stream and optionally shuffle each dataset

For each dataset in the manifest:

1. Open the dataset with the configured loader.
2. Apply `--sanity-check` / `--sanity-limit` if requested.
3. Apply manifest-level `max_documents` if present.
4. Apply the global `--max-documents-per-dataset` or per-dataset overrides from `--dataset-max-docs`.
5. Optionally bounded-shuffle the stream with `buffered_shuffle`.
   This uses a rolling buffer, so it avoids loading the whole dataset into memory.

### 3.2 Chunk long documents

Implementation: `processing/chunker.py`

For each raw document:

1. Count tokens with `tiktoken` `cl100k_base`.
2. If the document is short enough, keep it as-is.
3. If it exceeds `--max-chunk-tokens`, optionally chunk it.
4. Chunking first tries paragraph boundaries, then sentence/punctuation boundaries,
   then token-sized word splits as a fallback.
5. Chunks are accumulated toward `--target-chunk-tokens` while respecting
   `--min-chunk-tokens` and `--max-chunk-tokens`.
6. Chunks inherit the original author, source, language, and genre, and get
   `#chunk_<idx>` appended to `raw_id`.

If `--chunk-probability < 1.0`, some over-length documents are intentionally left
un-chunked.

### 3.3 Optional truncation

If `--truncate-to-tokens` is set, each chunk or original document is truncated
again using punctuation-aware boundaries. This keeps long records bounded even
when chunking is skipped.

### 3.4 Dirty filtering

Implementation: `processing/dirty.py`

Each chunk is checked for:

- zero length or no tokens
- low unique-token ratio
- high symbol ratio
- long symbol runs for PD-style sources
- long repeated character runs

Dropped rows are logged to `dirty_docs.log`. Per-row processing failures are
logged to `errored_docs.log`.

### 3.5 Author accumulation and author-count constraints

Implementation: `AuthorAccumulator` in `processing/build_benchmark.py`

This stage keeps only a bounded reservoir per author:

1. Hash each author as `sha256(source:author)`.
2. Keep at most 5 documents per author in memory.
3. Use reservoir replacement so late documents still have a chance to survive.
4. After all datasets are streamed, keep authors with at least 3 documents.
5. Re-add some underfull authors if they have at least 2 documents.
6. Still cap every kept author at 5 documents.

Current limits from `processing/config.py`:

- minimum docs per author: 3
- fallback minimum: 2
- maximum docs per author: 5

### 3.6 Internal build artifacts

After author filtering:

1. Documents are assigned deterministic `doc_id` values.
2. They are split into `train/dev/test` with `split_by_language`.
3. In the unified constructor, only `documents.jsonl` is written for each split.
   Retrieval files are intentionally skipped here.

Important implementation detail:

- These build-stage split files are an internal interchange format.
- The final stage later re-reads all build `documents.jsonl` files across splits
  into one pool and resamples/splits again.
- So the build split is not the final published split.

The build summary is written to:

- `<work_dir>/build_artifacts/processing_summary.json`
- `<work_dir>/build_artifacts/sampling_shortfall.json`

If `--work-dir` is omitted, this directory is temporary and auto-cleaned.

## 4. Stage 2: Quality Filtering

Implementation: `filter_documents` in `processing/postprocess.py`

The finalization stage starts by loading all build-stage documents back into a
single list with `_read_stage_documents`.

Quality filtering then applies the following sub-steps to every document:

1. Collapse letter-by-letter spacing artifacts such as `h e l l o` when the
   ratio or run length of single-letter tokens is too high.
2. Recompute token length and length bucket after normalization.
3. Drop documents that still have too many isolated single-letter tokens.
4. Re-run the dirty-text heuristics from stage 1.
5. Drop documents judged to be untranslatable or too low-information.

The "untranslatable" heuristic combines:

- low alphabetic character ratio
- low alphabetic token ratio
- excessive single-letter token runs
- low script match ratio for the labeled language
- optional `langdetect` verification during filtering unless `--post-skip-langdetect` is set

Dropped documents are recorded in `quality_filter_drops.log`.

## 5. Stage 3: Redundancy Reduction

Implementation: `processing/deduplication.py`

Redundancy reduction runs after quality filtering and before language audit.

### 5.1 Exact text dedup

1. Normalize text by case-folding and whitespace collapse.
2. Hash the normalized text.
3. Drop later exact duplicates.

### 5.2 Near-text dedup

For documents with at least `--dedup-min-tokens-for-near` tokens:

1. Compute a 64-bit SimHash over unigram and bigram features.
2. Use LSH buckets to generate candidate pairs.
3. Compare Hamming distance.
4. Drop documents whose distance is within the threshold implied by
   `--dedup-near-similarity-threshold`.

By default, near-text dedup is same-language-only. That can be relaxed with
`--dedup-allow-cross-language-near`.

### 5.3 Near-author dedup

This is author-profile dedup, not just document dedup:

1. Group remaining documents by `author_id`.
2. Build an author profile from up to `--dedup-author-profile-docs` representative docs.
3. Compute a SimHash for that profile.
4. Compare author profiles in LSH buckets.
5. By default, only compare authors across sources and within the same language.
6. When two author profiles look too similar, keep the stronger profile:
   more docs, then more total tokens, then lexical tie-break by author ID.

The result is one summary block with counts such as:

- input docs
- docs after exact/near document dedup
- docs after author dedup
- authors before and after
- matched pair counts
- drop reasons

## 6. Stage 4: Language Audit

Implementation: `processing/language_audit.py`

Language audit is separate from the earlier quality filter. Its job is to audit
the `lang` label and optionally retag or drop suspicious documents.

### 6.1 Detection sampling

The audit does not have to run `langdetect` on every document. It first selects
up to `--lang-audit-max-detect-docs` documents using a per-language balanced sample.

### 6.2 Audit checks

For each document:

1. Compute expected-script match ratio for the labeled language.
2. Mark low-script cases as suspicious once enough script-bearing characters exist.
3. If selected for detection and long enough, run `langdetect`.
4. If the detected language disagrees with the labeled language at or above
   `--lang-audit-min-confidence`, mark it as a mismatch.
5. Collect suspicious examples into `language_audit_suspects.jsonl`.

### 6.3 Retagging vs dropping

Default behavior:

- keep the document
- retag it to the detected language when the mismatch is high confidence

Optional strict behavior:

- pass `--lang-audit-drop-detected-mismatches`
- mismatched documents are dropped instead of retagged

The audit summary records:

- inspected docs
- mismatch rate
- low-script count
- suspicious count
- retagged pairs
- dropped docs
- per-language counters

## 7. Stage 5: Bucket Balanced Sampling

Implementation: `compute_language_targets`, `sample_documents`, and `write_outputs`
in `processing/postprocess.py`

This is where the actual benchmark size cap is enforced, the final train/dev/test
split is produced, and the retrieval files are written.

### 7.1 Resolve the final target

The final target is:

- `--post-target-total` if provided
- otherwise `--total-docs`

The target is capped at the number of available documents after audit.

### 7.2 Language targets

The code uses language weights from `processing/config.py`:

- `en 35%`
- `zh 10%`
- `es 10%`
- `ar 8%`
- `fr 8%`
- `ru 8%`
- `de 8%`
- `ja 5%`
- `ko 5%`
- `hi 3%`

If some target languages are missing or underfull, the budget is redistributed
across available languages according to those weights.

### 7.3 Genre and length balancing inside each language

Within each language, the sampler works hierarchically:

1. Compute a target for each genre using `GENRE_PERCENTS`.
2. Within each genre, compute targets for length buckets:
   `short`, `medium`, `long`, `extra_long`.
3. Sample available documents in each bucket.
4. Spill unmet quota into leftover documents from the same language when a bucket
   or genre is sparse.

Current length-bucket weights are:

- `short`: 15%
- `medium`: 50%
- `long`: 20%
- `extra_long`: 15%

### 7.4 Final split

After sampling:

1. Assign final `doc_id` values.
2. Split documents by language, genre, and length bucket into `train/dev/test`.
3. Default split ratios are `0.8 / 0.1 / 0.1`, unless overridden.

### 7.5 Retrieval export format

For the standard constructor output, each split contains:

- `candidates.jsonl`
- `queries.jsonl`
- `ground_truth.jsonl`

The constructor does not currently write final `documents.jsonl` files.

Final `candidates.jsonl` rows look like:

```json
{
  "candidate_id": "doc_000123",
  "author_id": "<sha256(source:author)>",
  "lang": "en",
  "genre": "news",
  "content": "<text>",
  "source": "babel_briefings",
  "token_length": 120
}
```

Final `queries.jsonl` rows look like:

```json
{
  "query_id": "doc_000456",
  "lang": "en",
  "genre": "news",
  "content": "<text>",
  "source": "babel_briefings",
  "token_length": 115
}
```

Final `ground_truth.jsonl` rows look like:

```json
{
  "query_id": "doc_000456",
  "positive_ids": ["doc_000123", "doc_000321"],
  "author_id": "<hashed_author>"
}
```

Query/candidate assignment is author-local:

- authors with fewer than 2 docs are skipped
- up to 2 docs become candidates
- up to 2 remaining docs become queries
- if no query remains, one candidate may be moved to the query side

## 8. Monitoring and Logs

`processing.construct_benchmark` writes two top-level reports:

- `pipeline_summary.json`
- `pipeline_dynamics.json`

`pipeline_summary.json` contains:

- build-stage summary
- finalize-stage summary
- stage 3 redundancy-reduction summary
- language-audit summary
- sampling deficits
- split summary

`pipeline_dynamics.json` contains:

- pipeline inputs and config knobs
- per-stage summaries
- explicit stage-transition totals
- end-to-end runtime

Other important artifacts:

- `quality_filter_drops.log`
- `language_audit_suspects.jsonl`
- build-stage `dirty_docs.log`
- build-stage `errored_docs.log`

## 10. Phase 2 Web Crawl Plus Construction

Primary module:

```bash
python -m processing.second_phase_web_crawling.run_pipeline \
  --stages crawl construct
```

Wrapper script:

- `processing/second_phase_web_crawling/scripts/run_phase2_construction.sh`

### 10.1 Crawl stage

The crawl stage can run any subset of:

- Stack Exchange
- Project Gutenberg
- Wikisource
- YouTube comments

After crawling, it always regenerates the phase 2 manifest with
`processing.second_phase_web_crawling.build_manifest`.

### 10.2 Construct stage

The construct stage is not separate logic. It delegates to
`processing.construct_benchmark` and forwards the relevant arguments.

So phase 2 uses the same stage 1 through stage 5 pipeline described above.

### 10.3 Wrapper-script behavior

`run_phase2_construction.sh` adds several operational behaviors around the core modules:

- loads `.env` and optional `.env.stackexchange`
- checks for `YOUTUBE_API_KEY` when YouTube crawling is enabled
- installs `langdetect` if missing
- requires `jq`
- supports safe-mode guardrails for Stack Exchange API usage
- supports auto-ramping crawl caps toward the requested target

The script currently defaults to a 600k target for both `--total-docs` and
`--post-target-total`.

## 11. Combining Phase 1 and Phase 2

Implementation: `processing/combine_phase_benchmarks.py`

This stage merges already-finalized phase outputs rather than rebuilding from raw data.

### 11.1 Load both finalized pools

The combiner reads stage documents from:

- `documents.jsonl` if present
- otherwise `candidates.jsonl` and `queries.jsonl` plus `ground_truth.jsonl`

For normal phase outputs, that means it reconstructs a document pool from the
retrieval files.

### 11.2 Optional retagging and per-phase dedup

Before merging, the combiner can:

- rerun language audit with `--retag-languages`
- deduplicate each phase independently unless `--disable-dedup` is set

### 11.3 Cross-phase overlap removal

By default:

1. Exact normalized-text overlap is checked across phases.
2. Phase 1 documents that exactly match phase 2 text are removed.
3. Phase 2 is preferred so new web-crawled coverage survives.

This behavior can be disabled with `--disable-cross-phase-overlap-removal`.

### 11.4 Phase share logic and sampling

If `--take-all-docs` is used:

- keep all surviving phase 1 and phase 2 docs
- skip phase-wise sampling

Otherwise:

1. Resolve the effective total.
2. Enforce `--min-phase2-share`.
3. Sample phase 1 and phase 2 separately using the same language balancing logic.

### 11.5 Combined export

After phase-wise selection:

1. Concatenate both pools.
2. Reassign IDs with the prefix `mix_`.
3. Split with `split_by_author_language`, so each author stays within one split.
4. Write:
   - `documents.jsonl`
   - `candidates.jsonl`
   - `queries.jsonl`
   - `ground_truth.jsonl`

Unlike the standard constructor output, the combined output does write
`documents.jsonl`, and it preserves all selected docs in the export.

Wrapper script:

- `processing/second_phase_web_crawling/scripts/run_combine_all_docs_phase1_phase2.sh`
